# Changelog

All user-visible Skarbiec changes are recorded here, newest first. Skarbiec
follows Semantic Versioning; while the major version is zero, a compatibility
boundary advances the minor version. Installation, channel, upgrade and
rollback rules live in [`docs/INSTALL.md`](docs/INSTALL.md).

`v0.1.3` is the only published release. Its GitHub release body is the
autogenerated line `**Full Changelog**: …/commits/v0.1.3`, produced by
`gh release create --generate-notes` in `.github/workflows/ci.yml`, so the
release shipped without written notes. The `0.1.3` section below was
reconstructed after the fact from the repository state at the tag and from the
Git history; it is marked as such. There is no earlier tag, so `0.1.3` is
described as the first released surface rather than as a delta.

## Unreleased

Derived from `git diff v0.1.3 HEAD` (14 commits, 68 files, +5352/-1941).

### Added

- Added `skarbiec routes list|add|reconcile|verify` (`src/access/routes.rs`),
  the command and operator-API surface over the capability routes table the
  broker resolves every resource through. `routes reconcile` derives missing
  `provider:*` and `agent:*` identity routes from the live vault and maps each
  provider family to its unique `-primary` credential; it never repoints an
  existing route or guesses between ambiguous candidates. `routes add` remains
  the deliberate path for non-derived mappings: it is idempotent, requires
  `--reason`, keeps the previous table, and records the reason beside the table
  and in the hash-chained audit journal. `routes list` and `routes verify`
  resolve every coordinate without returning values, distinguish unreadable
  items from missing fields, and expose the same answers to the desktop app.
  Documented under "Capability routes" in `docs/CLI.md`.
- Capability state now recovers from concatenated complete JSON snapshots left
  by an older interrupted writer. Skarbiec preserves the corrupt bytes, restores
  the newest complete snapshot atomically, and resumes short-lived capability
  issuance instead of disabling every provider indefinitely.
- Added the canonical item kind `host-account` (`src/core/schema.rs`) for the
  operating-system account of a fleet host: `username` and `password` are both
  required, and `context.account_ref` must name `<user>@<host>` so the credential
  can be matched to the registry target that points at it. It is a separate kind
  from `login` because login trajectories enumerate `login` items to drive
  browsers and must never find a machine account among them. The convention —
  registry `account_ref` names the item, transcripts are not a credential store —
  is documented under "Fleet host accounts" in `docs/CLI.md`.
- Added an explicit vault-format migration, `skarbiec migrate-v2`
  (`src/core/migrate.rs`, `src/core/schema.rs`), which rewrites the vault
  document to `"version": "v2"`.
- Added a guided first-use onboarding journey, `skarbiec onboarding`
  (`src/onboarding.rs`, `src/onboarding_first_use.json`): four screens —
  promise, capability model, safe demo, audit proof — emitting
  `onboarding_step_viewed`, `onboarding_step_completed`,
  `onboarding_completed` and `onboarding_first_success_observed`.
- Added `docs/examples/acquire-one-field.sh`.

### Fixed

- The `item-write` journal entry added to name the process behind a vault write
  named nobody, so the two subscription items whose enumeration tags kept
  disappearing could not be attributed after all. Three faults, all in
  `src/core/vault.rs`: the entry was queued with `append` rather than
  `append_sync`, and a one-shot CLI write -- which is what every rotation on this
  fleet is, `set-json` invoked once per credential refresh -- exits before the
  worker thread journals it, so a subscription item at revision 318 had produced
  no journal line at all; `parent_process_id` read `ps -o ppid=,command= -p
  <self>`, whose single row describes this process, and then kept only its first
  whitespace-separated token, so the record carried a bare parent pid and never
  the parent command its own documentation promised; and the recorded tag count
  was the count the caller passed rather than the count the revision stored, so a
  tag-preserving write looked like a write that had dropped every tag. The entry
  now journals synchronously and carries `parent_pid`, `parent_process` (the
  parent's program only -- never the rest of its argument vector, which may carry
  a secret), `tags` as stored and `tags_requested` as asked for, so the next
  disappearance names its own writer instead of costing another night of guessing.
- A credential operation whose submit or resume never reached Weles (bridge
  invocation error) was recorded with the plain status `failed`, which no
  settlement path matched: the item kept its staged revision and stayed
  `adopting`/`pending` forever, refusing every later lifecycle command. Those
  paths now record `operation_failed`, and `credential status` settles records
  carrying either spelling through the existing rollback
  (`src/credential/lifecycle.rs`, `src/credential/status.rs`).
- A published binary reported `commit: null`, so nothing could tell a build that
  came through the release channel from one somebody compiled by hand. The
  builder compiles an extracted `git archive HEAD` snapshot, which carries no
  `.git` directory, and Stado's build environment names no revision, so
  `SKARBIEC_RELEASE_COMMIT` was never set and `option_env!` resolved to nothing.
  `.release-commit` now carries `$Format:%H$` and is marked `export-subst` in
  `.gitattributes`, so git substitutes the revision into the archive itself, and
  `scripts/release/build.sh` stamps it (falling back to `git rev-parse` in a
  checkout, and refusing to build a release that cannot name its source). This is
  what let a side-loaded 0.2.1 pass for a managed binary on the operator laptop
  for four days while every credential rotation it performed dropped the
  `brama:agent:<id>` tags that bind a subscription to its agent.
- `skarbiec version` reported `provenance: "published"` for a released build.
  Every surface that classifies host software uses `release` against `unmanaged`,
  so the reporting side had to match a word no other surface used; a released
  build now reports `provenance: "release"`. An unpublished build still reports
  `source build` rather than guessing.
- `scripts/release/quality.sh` could not pass, so the product could not be
  released at all: `cargo fmt --check` reported five files and
  `cargo clippy -- -D warnings` three errors, none of them in code being changed
  here (`src/access/capability.rs`, `src/core/items.rs`, `src/core/vault.rs`,
  `src/credential/status.rs`, `src/credential/state.rs`,
  `src/credential/tests.rs`). Formatting is now canonical, the two
  `unnecessary_to_owned` call sites pass the `&str` constants directly, and
  `authorize_managed_write` answers `too_many_arguments` with a documented
  `#[allow]` rather than a struct that would rename the same eight coordinates.

### Changed

- The default vault location moved from `$HOME/.stado/skarbiec.vault.json` to
  `$HOME/.local/share/skarbiec/skarbiec.vault.json`. `SKARBIEC_VAULT_FILE`
  still overrides it.
- Acquisition identifiers are canonicalized from `request:credential/…` to
  `operation:credential/…` as part of the v2 migration.
- `src/access/tokens.rs`, `src/core/vault.rs`, `src/credential.rs` and
  `src/net/mod.rs` were substantially rewritten.
- The `error_code` values the local HTTP API emits, and the rule that bounds a
  `detail`, now come from the shared `wisent-errors` package (pinned by commit
  in `Cargo.toml`) instead of being spelled out in `src/net/`. No emitted code,
  status, message or bound changed: the same four codes go out on the same five
  replies, and the seven codes' severity, retryability and outage flags are
  identical to the table skarbiec's callers already applied. The one behavioural
  difference is that a `detail` with leading or trailing whitespace now has it
  stripped before the 400-character cut, which no message skarbiec composes can
  produce except a bridge diagnostic whose own 512-character cut lands on a word
  boundary (`src/net/mod.rs`, `src/net/http.rs`, `src/net/mcp.rs`,
  `src/credential/wire.rs`).

### Removed

- Removed wildcard scope matching (`glob_matches` in `src/core/mod.rs`). Bond
  grants now bind to exact resources.
- Removed `scripts/publish.sh` and seven example scripts, including the whole
  `docs/examples/weles/` directory.

### Data and state migrations

- `migrate-v2` writes a snapshot of the pre-migration vault to
  `<vault>.pre-v2.<epoch>` before rewriting, decrypts and re-writes historical
  revisions, and reports the item, revision and grant counts it touched.
  `--snapshot` overrides the snapshot path. The migration refuses to run if the
  snapshot path already exists, so it cannot silently overwrite a recovery
  point.

### Operator actions

- Move an existing vault to the new default path, or set
  `SKARBIEC_VAULT_FILE` to its current location, before first use of this
  revision.
- Run `skarbiec migrate-v2` and keep the `.pre-v2.<epoch>` snapshot until the
  migrated vault has been verified with `key-doctor` and `verify-chain`.
- Re-express any wildcard bond grant as exact resources; wildcard scopes no
  longer match.

### Known limitations

- No immutable release has been published from this revision.
- `released-surface.json` still describes the 62 commands of `0.1.3` and does
  not list `migrate-v2` or `onboarding`.

## 0.1.3 - 2026-08-01

Reconstructed from the repository state at tag `v0.1.3` (`Cargo.toml`
`version = 0.1.3`, annotated and SSH-signed tag `Skarbiec v0.1.3`), from
`released-surface.json` recovered from the published artifact, and from
`docs/INSTALL.md` — the release itself was published without notes. This is the
first published tag, so there is no previous release to diff against: the
"Added" section below describes the released surface as a whole, and no
"Changed" or "Fixed" section can be derived from Git for it.

### Added

The released command surface is the 62 commands recorded in
`released-surface.json`, recovered by downloading
`stado:releases/skarbiec/0.1.3/darwin-arm64/skarbiec` and asking the published
binary for its own command list. Grouped by capability:

- **Vault items** — `init`, `set`, `set-json`, `get`, `list`, `delete`,
  `purge`, `restore`, `restore-version`, `status`, `version`. Values are stored
  as armored ciphertext sealed to the recipients' public keys; item history is
  kept inside the v1 document format and `restore-version` reads a point in
  time.
- **Recipients and sharing** — `add-user`, `users`, `share`, `revoke`,
  `invite`, `export-key`. Sharing and revocation re-encrypt the affected
  ciphertext rather than gating access at read time.
- **Scoped service-account grants** — `token-mint`, `token-verify`,
  `token-revoke`, `tokens`, `credential`, `acquisition-request`,
  `acquisition-read`. Read, write and delete are checked independently. A
  request-only grant issues a short-lived bearer bound to one field and
  consumed atomically on the first successful read.
- **Ownership rotation** — `rotate-owner` re-wraps every current and historical
  ciphertext for the new owner, drops the previous owner per item, preserves
  the recovery recipient, and writes all-or-nothing.
- **Recovery and emergency access** — `emergency-grant`, `emergency-activate`,
  `emergency-cancel`, `emergency-list`, `recovery-status`, `recovery-drill`,
  `key-doctor`. Emergency grants are time-delayed. `key-doctor` reports which
  keys actually open the vault and names the
  `private-keys-v1.d/<KEYGRIP>.key` files needed to reproduce that, reading the
  document and keyring directly instead of going through the API.
- **Bonds and donations** — `bond-add`, `bond-list`, `bond-remove`, `bonds`,
  `donate`, `donation-accept`, `donation-reject`, `donations`, `enroll`.
- **Policy and audit** — `policy-get`, `policy-set`, `policy-check-length`,
  `audit`, `audit-query`, `verify-chain`. The audit log is append-only and each
  line carries the hash of its predecessor, so `verify-chain` detects a
  retroactive edit.
- **Runtime injection** — `resolve` writes an owner-only env file and returns
  its path; `expand` fills a template. Secret values never reach stdout.
- **Utilities** — `generate` (OS entropy), `totp` (one-time codes from a stored
  seed), `breach-check` (k-anonymous: only a hash prefix leaves the host).
- **Sync** — `sync-init`, `sync-push`, `sync-pull`, `sync-status`,
  `sync-daemon`, `pull`. Git-backed; only ciphertext crosses the network.
- **Servers and browser integration** — `serve` (local HTTP API), `mcp` (stdio
  MCP), `native-host`, `browser-host-install`. The HTTP and MCP surfaces share
  one policy and audit core.

Published artifacts under this tag: `skarbiec-v0.1.3-linux-amd64.tar.gz`,
`skarbiec-v0.1.3-darwin-arm64.tar.gz`, a sibling `.sha256` for each, the
autofill extension `skarbiec-autofill.crx` with its `.sha256` and the Omaha
update manifest `skarbiec-autofill.xml`, and
`skarbiec-entitlements-router-linux-amd64`. Each archive contains the binary,
`LICENSE`, `NOTICE` and `TRADEMARKS.md`. There is no mutable `latest`
artifact.

### Removed

- The bootstrap-bearer contract was removed by the cutover to workload-proof
  acquisition. `docs/INSTALL.md` states this explicitly as the reason the
  release takes the next compatibility boundary instead of a patch bump.

### Security-relevant changes

- All cryptography is delegated to `gpg`, `openssl` and `shasum`; the product
  ships no primitives of its own.
- Acquisition state holds only hashes and scope metadata and must stay an
  owner-only regular file.
- `breach-check` is k-anonymous: only a hash prefix leaves the host.
- The audit chain is tamper-evident and verifiable offline with `verify-chain`.
- Public release assets are bearer-free; the Chrome extension signing key
  exists only as the repository secret
  `SKARBIEC_EXTENSION_PRIVATE_KEY_B64`, and publication is refused when the
  extension id derived from the public key does not match
  `deploy/chrome-extension-id`.
- `GET /health` opens real key material rather than reporting liveness only. An
  item that exists but cannot be decrypted returns `503 infra_down` instead of
  dropping the connection, so a key outage is distinguishable from a missing
  item.
- The published binary carries its provenance: `SKARBIEC_RELEASE_URI` (the
  immutable asset URL) and `SKARBIEC_RELEASE_COMMIT`. Without them the binary
  reports itself as a source build rather than as published.

### Configuration changes

Seven variables, all optional except where a feature is being enabled
(`.env.example`):

- `SKARBIEC_VAULT_FILE` — vault path; defaults to
  `~/.stado/skarbiec.vault.json` in this release.
- `SKARBIEC_UNLOCK` — passphrase for a single decrypt.
- `SKARBIEC_UNLOCK_FILE` — passphrase file, preferred for a long-running
  service under launchd or systemd.
- `SKARBIEC_ACQUISITION_TTL_SECONDS`, `SKARBIEC_ACQUISITION_FILE` — one-shot
  acquisition control.
- `SKARBIEC_MCP_CONSUMER`, `SKARBIEC_MCP_TOKEN`, `SKARBIEC_MCP_TOKEN_FILE` —
  all three are required together to enable `resolve` over MCP; plus
  `SKARBIEC_MCP_OUT_DIR`.
- `SKARBIEC_INSTALL_DIR` overrides the install target
  (`$HOME/.stado/bin`).

### Data and state migrations

- None. The vault document format is `v1` at this tag and no migration code
  exists in it.

### Compatibility requirements

- `gpg`, `openssl` and `shasum` must be on `PATH`. `oathtool` is optional and
  needed only for one-time codes.
- Supported platform coordinates are `linux-amd64` and `darwin-arm64` only.
- A deployment must pin the exact tag, platform, archive URL and checksum.
  There is no `latest`, so no host resolves a moving label.
- An upgrade replaces the binary out of band: the supervisor stops the
  service, downloads and verifies the pinned artifact, swaps the binary
  atomically, restarts and runs `key-doctor`. Skarbiec never replaces its own
  executable while serving a request.
- Rollback is pointing the configured tag at an earlier release; the rollback
  coordinate stays explicit and is not automated.

### Operator actions required

- Run `skarbiec key-doctor` and `skarbiec recovery-status` immediately after
  installing.
- Export the recovery secret and remove it from the local keyring before
  storing real data — see the known limitation below.
- For the browser path, run `skarbiec browser-host-install`, which mints or
  rotates only the `read:login-*` grant and atomically writes owner-private
  native-messaging manifests for Chrome and Firefox. Managed deployment uses
  `deploy/chrome-managed-policy.json` with `ExtensionInstallForcelist`.
- Do not point a deployment at a new coordinate until its public assets and
  checksums are visible.

### Known limitations

- The release itself shipped without notes; this section is the reconstruction.
- `init` generates the owner key and the recovery key into the *same* local
  keyring, so until the operator exports the recovery secret and removes it
  from that keyring, one directory holds both halves of the failure domain.
  `recovery-status` treats a local recovery secret as a fault.
- Item metadata inside the vault file is not secret; only values are
  encrypted.
- `released-surface.json` omits `import`, `export` and `help`, which the tagged
  `src/main.rs` does accept, so the recorded surface is narrower than the
  binary's real command set.
- `docs/CLI.md` mixes Polish section headings into an otherwise English
  document.
- `docs/ARCHITECTURE-REVIEW.md` ships as part of the release and ranks known
  defects by what can destroy or leak the vault.
